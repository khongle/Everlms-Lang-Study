# B05 — Acceptance Criteria for F-011 — Mobile App

> Per-feature Given/When/Then criteria grounded in code. Backend module: `lms_mobile_api` (all routes under `/api/v1/`). Flutter client: `app/` (v1.0.10+33, Riverpod/GoRouter/Dio, 33 screens).
>
> Auth mechanism: custom bearer token via `keyvalue.expirable` (collection `lms_mobile_api.tokens`, default 7-day TTL) — NOT OAuth2/JWT despite unused `oauth_client_id`/`oauth_client_secret` config keys.

---

## AC-112: Mobile registration with OTP email verification

**Priority:** Must
**Given** the Flutter app sends POST `/api/v1/user/register` with `{email, password (≥8 chars), password_confirm}`
**When** `MobileAuthController::register()` processes the request
**Then** if the email is unique and passwords match, a blocked Drupal user (status=0, role=`student`) is created; a 6-digit OTP is generated by `OtpService::generateOtpCode()` and emailed via `hook_mail` (key `otp_email`, type `register`, subject "Your EverLMS verification code"); response returns `{status: "otp_sent", otp_token: string}`
**And** if the email already belongs to an active account, a 422 `{error: "validation_error", violations: [{field, message}]}` response is returned without creating a duplicate

---

## AC-113: OTP verification activates account and issues bearer token

**Priority:** Must
**Given** the Flutter app received an `otp_token` from registration
**When** the user submits POST `/api/v1/user/register/verify-otp` with `{otp_token, otp_code}`
**Then** `MobileAuthController::verifyRegisterOtp()` validates the OTP session from `keyvalue.expirable` (collection `lms_mobile_api.otp`, 15-minute TTL); on match it activates the user (status=1), issues a 32-char hex bearer token stored in `keyvalue.expirable` collection `lms_mobile_api.tokens` (default 7-day TTL), and returns `{status: "verified", uid, access_token, token_type: "Bearer", expires_in}`
**And** on mismatch or expired OTP, returns HTTP 400 `{error: "invalid_otp", message: string}`

---

## AC-114: OTP resend invalidates previous token and issues new one

**Priority:** Must
**Given** a registration OTP session exists with a current `otp_token`
**When** the Flutter app sends POST `/api/v1/user/register/resend-otp` with the current `otp_token`
**Then** `MobileAuthController::resendRegisterOtp()` generates a new OTP code and a new session token; the old session is deleted (old token invalidated); a new OTP email is sent; response returns `{status: "otp_resent", otp_token: <new_token>}`
**And** using the old `otp_token` after resend returns HTTP 400 `{error: "invalid_otp"}`

---

## AC-115: Password login — email/password credential exchange for bearer token

**Priority:** Must
**Given** a Flutter client sends POST `/api/v1/oauth/token` with `{username: <email>, password}`
**When** `MobileAuthController::oauthToken()` processes the request
**Then** the user is looked up by email in `users_field_data`; password is verified via Drupal's `password` service; on success a bearer token is issued and response returns `{uid, email, name, access_token, token_type: "Bearer", expires_in}`
**And** on invalid credentials, HTTP 401 `{error: "invalid_grant", message: string}` is returned

---

## AC-116: Forgot-password — OTP flow to reset token to auto-login

**Priority:** Must
**Given** a Flutter user requests password reset via POST `/api/v1/user/forgot-password` with `{email}`
**When** `MobileAuthController::forgotPassword()` processes the request
**Then** the response is always HTTP 200 regardless of whether the email exists (prevents enumeration); for a valid active user, an OTP is generated and emailed (type `forgot_password`, subject "Your EverLMS password reset code"); `otp_token` is included in response body (empty string for unknown email)
**When** the user submits POST `/api/v1/user/forgot-password/verify-otp` with the correct OTP
**Then** a 30-minute `reset_token` (64-char hex, stored in collection `lms_mobile_api.reset`) is issued and returned
**When** the user submits POST `/api/v1/user/reset-password` with `{reset_token, password, password_confirm}`
**Then** password is updated; reset session is deleted; a new bearer token is issued for auto-login

---

## AC-117: Bearer token auth via X-Authorization / Authorization header fallback

**Priority:** Must
**Given** a Flutter client has a valid bearer token
**When** it sends a request to any protected endpoint with header `X-Authorization: Bearer <token>` or `Authorization: Bearer <token>`
**Then** the controller's private `getAuthenticatedUser()` reads `X-Authorization` first, then falls back to `Authorization`; the token is looked up in `keyvalue.expirable`; the active Drupal user is loaded
**And** a missing, invalid, or expired token results in `AccessDeniedHttpException` (HTTP 403)

> **Design note:** `X-Authorization` is checked first to work around server-level HTTP Basic Auth gates that intercept the `Authorization` header. Flutter clients should send both headers for maximum compatibility.

---

## AC-118: No refresh token mechanism (as-built — gap)

**Priority:** Must (document current state)
**Given** a bearer token has a 7-day TTL (604800 seconds, configurable via `lms_mobile_api.settings:token_expiry_seconds`)
**When** the token expires
**Then** the Flutter client must re-authenticate via `/api/v1/oauth/token`; there is no refresh token endpoint and no token renewal mechanism
**And** `oauth_client_id` / `oauth_client_secret` in `lms_mobile_api.settings.yml` are unused artifacts of an earlier OAuth2 design

---

## AC-119: Course search with multi-param filtering and pagination

**Priority:** Must
**Given** a Flutter client (authenticated or not) sends GET `/api/v1/courses/search`
**When** `MobileCourseController::searchCourses()` processes optional query params: `search`, `category[]`, `level[]`, `price[]` (free/paid), `sort` (newest|popular|rating|price_asc|price_desc), `page` (0-based), `limit` (1–100, default 20), `featured`
**Then** only published (`status=1`) courses are returned; all filters and sort are applied; response: `{total, page, limit, items: CourseListItem[]}` where each item includes `id, uuid, title, short_description, thumbnail_url, price, price_type, level, category, instructor, rating, rating_count, student_count, duration_minutes, bestseller, featured, created`

---

## AC-120: Category listing with per-category course count

**Priority:** Must
**Given** a Flutter client sends GET `/api/v1/categories`
**When** `MobileCourseController::listCategories()` runs
**Then** published `course_category` taxonomy terms are returned sorted by `weight` then `name`; each item includes: `id, uuid, name, description, thumbnail_url` (from `field_category_thumbnail`), `course_count` (count of published courses in that category)

---

## AC-121: Course detail — curriculum with drip-lock and enrollment state

**Priority:** Must
**Given** a Flutter client sends GET `/api/v1/courses/{courseId}`
**When** `MobileCourseController::getCourseDetail()` processes the request
**Then** the response includes: full course metadata, curriculum (chapters + lessons with `is_completed`, `is_locked`, and drip-lock calculated from `field_drip_days` vs `field_enrolled_at` per lesson position), and if authenticated: `enrollment: {enrolled, progress, status, last_lesson_id}` and `is_wishlisted`
**And** an unpublished or non-existent course returns HTTP 404

---

## AC-122: Free course enrollment via mobile API

**Priority:** Must
**Given** an authenticated Flutter client sends POST `/api/v1/courses/{courseId}/enroll-free`
**When** `MobileCourseController::enrollFree()` processes the request
**Then** it verifies `field_price_type === 'free'`; checks no existing `lms_user_course` record; finds the first published lesson; creates a `lms_user_course` entity with `field_progress=0.0`, `field_status='enrolled'`; returns `{status: "enrolled", course_id, enrollment_id, first_lesson_id}`
**And** if the course is paid (not free), HTTP 403 is returned; if already enrolled, HTTP 400 `{error: "already_enrolled"}`

---

## AC-123: Lesson detail — drip-lock returns HTTP 423 with unlock timestamp

**Priority:** Must
**Given** a course has `field_drip_days` set (e.g. 7 days between lessons)
**When** an enrolled Flutter student requests GET `/api/v1/courses/{courseId}/lessons/{lessonId}` for a lesson not yet unlocked
**Then** `MobileLearningController::getLessonDetail()` calculates the unlock timestamp from `field_enrolled_at` + (lesson_position * drip_days * 86400 seconds); if not yet unlocked, returns HTTP 423 `{error: "lesson_locked", message: string, unlocks_at: ISO8601 datetime}`

**Given** a lesson has `field_free_preview = TRUE`
**When** an unauthenticated or non-enrolled client requests the lesson
**Then** the lesson content is returned without an enrollment check; `is_locked=false` in the response

---

## AC-124: Quiz submission — grading via GradingStrategyFactory with 8 bundle types

**Priority:** Must
**Given** a Flutter student sends POST `/api/v1/quiz/{quizId}/submit` with `{answers: [...], time_taken_seconds}`
**When** `MobileLearningController::submitQuiz()` processes the submission
**Then** `GradingStrategyFactory::getStrategy(question.bundle())` is called for each of the 8 question bundles (`single_choice`, `multiple_choice`, `true_false`, `matching`, `ordering`, `fill_blank`, `short_answer`, `essay`); a `lms_question_response` is created per question; a `lms_quiz_result` entity is saved with `field_score`, `field_result` (from `quiz_results` taxonomy term lookup), and time fields
**And** if the quiz passes, `QuizPassedEvent` is dispatched (if the class exists), triggering certificate issuance and quiz-result notification

> **Dependency gap (as-built):** `lms_mobile_api` uses `GradingStrategyFactory` and `QuizPassedEvent` from `lms_quiz`, but `lms_quiz` is NOT listed as a dependency in `lms_mobile_api.info.yml`. Module load order is not guaranteed.

---

## AC-125: Progress mark-complete — recalculates course progress and status

**Priority:** Must
**Given** an enrolled Flutter student sends POST `/api/v1/progress/mark-complete` with `{course_id, lesson_id}`
**When** `MobileLearningController::markLessonComplete()` processes the request
**Then** a `lms_user_lesson` record is created or updated with `field_status='completed'` and `field_completed_at=now`; course progress % is recalculated (completed_count / total_lesson_count * 100); `lms_user_course.field_progress` is updated; if 100% the course status is set to `completed` and `field_completed_at` is set; if between 1–99% and was `enrolled` the status transitions to `in_progress`
**And** response: `{success: true, lesson_completed: bool, course_completed: bool, progress: float, next_lesson_id: int|null, next_lesson_url: string|null}`
