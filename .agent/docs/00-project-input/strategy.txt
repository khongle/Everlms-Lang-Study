1. BỨC TRANH CHIẾN LƯỢC — 3 MẢNH GHÉP
--------------------------------------------------------------------------------
MẢNH 1 — SẢN PHẨM [AS-BUILT]
  EverLMS: Drupal 11 modular monolith, 28 module lms_*, 29 entity, 7 role,
  quiz engine 8 loại câu hỏi, chứng chỉ PDF (mPDF) event-driven idempotent,
  commerce tự viết (Stripe chạy được), app Flutter + REST /api/v1 (~22 route,
  OTP/bearer). 13 epic phần lớn done; partial: badges (E05), webhooks (E06),
  notifications (E09), analytics (E12). Test tự động ~0%.

MẢNH 2 — BẰNG CHỨNG THỊ TRƯỜNG [AS-BUILT, xác minh 2026-07-15]
  lms.jfcsystem.com.au = EverLMS chạy production cho JFC Australia/New Zealand
  (tập đoàn thực phẩm Nhật, HQ Sydney) ở chế độ "đào tạo an toàn & tuân thủ
  NỘI BỘ": 17 khóa miễn phí (HACCP, Forklift, Manual Handling, Cybersecurity),
  login-only, không bán khóa. Phân nhóm bằng course category theo bộ phận
  (All Employees / Warehouse / Driving / Customer Service).
  => Ý NGHĨA CHIẾN LƯỢC: sản phẩm đã được chứng minh ở ĐÚNG phân khúc Nissei
  cần (công ty Nhật + đào tạo tuân thủ nội bộ + đa pháp nhân AU/NZ). JFC là
  reference case; Nissei là khách hàng #2 của cùng một "mode".
  Lưu ý học được từ JFC: category "Merged, Do Not Use" còn treo trên catalog
  → dấu hiệu thiếu cơ chế phân vùng thật và data hygiene; Nissei ở quy mô
  5.000+ người sẽ không sống được bằng cách phân nhóm bằng category.

MẢNH 3 — KHÁCH HÀNG MỤC TIÊU [xem company-info.txt + consulting.txt]
  Nissei Electric: 3 nhà máy VN (~5.000+ công nhân) + 2 VP thương mại TQ.
  Nỗi đau: đào tạo không đồng bộ giữa chi nhánh. Ràng buộc: chỉ triển khai
  VN+TQ, quyết định thật ở HQ Hamamatsu. Nhu cầu lõi: 6 tiêu chí đồng bộ
  D1–D6 (consulting.txt mục 2) — danh mục khóa master, ma trận đào tạo theo
  vị trí, hồ sơ đào tạo duy nhất theo nhân viên, chuẩn chứng chỉ + chu kỳ
  tái đào tạo, báo cáo tuân thủ hợp nhất, quy trình nội dung trung tâm.

ĐỊNH VỊ [DECISION đề xuất]:
  Phát triển EverLMS thành nền tảng có 2 chế độ triển khai chính thức:
    Mode A — "Academy" (bán khóa học, catalog công khai, commerce): như demo.
    Mode B — "Enterprise Compliance Training" (nội bộ, miễn phí, multi-branch,
             hồ sơ tuân thủ): JFC đã chạy dạng sơ khai, Nissei là khách kéo
             product lên chuẩn. KHÔNG làm multi-tenant SaaS (giữ non-goal
             trong A02) — mỗi khách 1 instance; "multi-branch" là phân vùng
             NỘI BỘ một tổ chức, không phải tenancy.
  Deal Nissei được dùng làm đòn bẩy: mọi tính năng mới đi vào PRODUCT CORE
  (JFC cũng hưởng lợi → upsell), không fork riêng cho Nissei.

3. QUYẾT ĐỊNH KIẾN TRÚC CHIẾN LƯỢC [DECISION — cần SA chốt]
--------------------------------------------------------------------------------
AD-S1. Multi-branch đi vào PRODUCT CORE, không fork.
  Module mới đề xuất: lms_organization (theo chuẩn lms_* + plugin pattern).
  - Entity lms_branch (hoặc vocabulary + entity reference — chọn khi thiết kế;
    thiên về ENTITY vì cần metadata: mã site, quốc gia, timezone, ngôn ngữ).
  - field_branch (entity ref) trên user + các entity vận hành (enrollment,
    quiz_result, user_certificate); course KHÔNG thuộc branch (danh mục master
    dùng chung — đúng nguyên tắc "chuẩn trung tâm, thực thi địa phương").
  - Role scoping: thêm biến thể quyền "in own branch" cho manager/instructor
    (mở rộng mô hình own/all sẵn có trong permission-registry).
  - Rủi ro kiến trúc: đụng access-control của toàn bộ route hiện hữu → phải
    có test baseline (W03) TRƯỚC khi làm. Đây là lý do kỹ thuật để kéo R-006
    vào phạm vi deal.

AD-S2. Compliance là module mới lms_compliance, không nhét vào certificate.
  - Training matrix: job_role (vocabulary mới) x course bắt buộc x chu kỳ.
  - Hạn hiệu lực chứng chỉ + trạng thái due/overdue + event nhắc hạn (nối vào
    lms_notification email channel).
  - Báo cáo: mở rộng lms_analytics thêm compliance KPIs per-branch — trùng
    luôn task E12S01T01 đang mở trong queue.
  - Đây là DIFFERENTIATOR của Mode B — thứ JFC chưa có, bán lại được cho JFC.

AD-S3. Đa ngôn ngữ: bật core i18n stack (language + locale + content_translation
  + config_translation), KHÔNG tự chế. 7 entity đã translatable là lợi thế;
  việc lớn nằm ở: dịch UI string VI/JA/ZH, template email/notification đa ngữ,
  Flutter app l10n (framework l10n đã có trong app — cần bật locale mới),
  mPDF font CJK, và QUY TRÌNH dịch nội dung (D6 trong consulting.txt).

AD-S4. Chuỗi giá trị theo instance: mỗi khách 1 instance tự host (giữ non-goal
  không SaaS). Nissei: instance đặt tại VN (NĐ 13/2023 + độ trễ), user TQ dùng
  web. Không dựng hạ tầng đại lục cho 2 VP (xem consulting.txt 5.1).

AD-S5. Mô hình docs "product core + customer project" — LỖ HỔNG FRAMEWORK.
  LodeStar hiện là quy trình build docs cho MỘT dự án; không có khái niệm
  re-instantiate cho khách mới (đã xác minh 2026-07-15). Đề xuất mở rộng
  (đưa vào ideas/ của framework, GIỮ NGUYÊN nguyên tắc IP: 00-Guidelines
  không ship cho khách, docs khách hàng là bản distilled):
  - Repo product (repo này): giữ nguyên tree A–U+Z = tài liệu SẢN PHẨM.
  - Mỗi khách = 1 project tree riêng chạy lại recipe, trong đó 00-project-input
    của khách chứa: company-info, consulting, strategy (3 file này chính là
    khởi đầu của pattern đó), khảo sát GĐ 0, và THAM CHIẾU docs product như
    nguồn as-built (giống rebuild-mode đã có sẵn trong framework).
  - Delta khách (config, theme skin, nội dung khóa) tách khỏi core bằng
    config split / recipe Drupal — tránh lặp lại tình trạng JFC (không rõ
    JFC instance đang lệch core bao xa — CẦN KIỂM KÊ, xem mục 6).

ro kiến trúc (branch, i18n) làm sớm khi có test baseline; (3) không build cái
chưa hỏi khách (SSO, offline, Zoom).

WAVE S0 — SALES ENABLER (làm ngay, trước/không phụ thuộc hợp đồng)
  S0.1 Xử lý R-001: chuyển toàn bộ secrets sang Key module / env override,
       ROTATE mọi key đã lộ trong git history (Stripe, PayPal, Zoom, OpenAI,
       Gemini, Google OAuth). Điều kiện sống còn để qua security review Nhật
       — và là task W01 sẵn có trong queue. [G6]
  S0.2 Demo instance kịch bản Nissei: 2 branch mẫu (giả lập bằng category
       như JFC làm — chấp nhận tạm cho demo), ma trận ATLĐ nhóm 1–6, nội dung
       VI, mẫu chứng chỉ song ngữ VI/JA tĩnh. Demo đúng nỗi đau (consulting.txt

  S0.3 Spike kỹ thuật 3 mục: (a) mPDF render font JA/ZH trong template chứng
       chỉ hiện tại [G7]; (b) bật language+content_translation trên bản dev,
       đo mức vỡ của theme/views [G2]; (c) audit tài nguyên Google-hosted
       trong lms_theme + app [G9]. Output: 3 spike note vào docs.
  S0.4 Kiểm kê delta instance JFC so với core (xem mục 6).

WAVE S1 — NỀN MÓNG ENTERPRISE (khi có hợp đồng GĐ 1–2 của consulting.txt)

       (kéo W03/R-006 lên sớm — điều kiện kỹ thuật của S1.2). [G6]
  S1.2 lms_organization: branch entity + field trên user/enrollment/result/
       cert + quyền "in own branch" + branch switcher cho manager. [G1]
  S1.3 Bulk user import CSV (mã NV, tên, branch, job_role, email/phone) +
       màn hình đối soát lỗi — ăn khớp audit master data GĐ 0. [G5]
  S1.4 Email channel + SMTP cấu hình chuẩn (W02/R-005 sẵn trong queue). [G8]

WAVE S2 — COMPLIANCE CORE (pilot GĐ 2)

WAVE S3 — ĐA NGÔN NGỮ (rollout GĐ 3–4)

  S3.2 mPDF CJK production-grade + template chứng chỉ đa ngữ. [G7]
  S3.3 Flutter app: bật locale VI/JA/ZH, rebrand Nissei, phân phối
